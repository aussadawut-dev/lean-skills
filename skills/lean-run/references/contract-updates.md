# Contract updates during a run

## Working record

Use the latest contract in the conversation as the working record. Incorporate new user messages in arrival order. A batch can share one recap if it arrives before the next affected action.

## Steps

1. **Merge the change.** Add new requirements to the active task by default. Apply a clear correction, answer or cancellation to its specific item. Keep other deliverables, questions, acceptance, constraints and destination. Answer status requests without changing scope. If the user explicitly pauses, cancels or switches tasks, follow that direction and record what was left open for any task that may resume.
2. **Refresh evidence.** Invalidate checks, review and approvals tied to changed scope or artifacts where they no longer apply. Reuse evidence that still matches. Keep task-wide repair counts and authority limits. If a worker or operation is already running, update its scope where supported or inspect its outcome before reusing or retrying it. Ask only about consequential ambiguities and continue independent work.
3. **Post the recap.** Post one short `Recap:` containing the merged requirements, including completed, pending and blocked items. Retain constraints and the delivery destination wherever they affect the work. Name explicit replacements or removals when they happen so the user can spot a dropped item. Continue authorized work after the recap. Keep the record in chat unless the user or an existing project record requires persistence.

## Updater example

```text
Recap: Right panel fixed and verified. Explain the interrupt and confirm the
live Canvas workflow (both open). Add Shut down and Restart to update (open).
Check GitHub commits for updates. Deliver verified changes in this workspace.
```

## Closing items

Use this contract to decide what still needs action before delivery. An unanswered decision or a check of superseded behavior cannot close an item.
