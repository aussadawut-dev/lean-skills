# Product and UX acceptance

Use when the request concerns product discovery or user-facing behavior. Apply only dimensions that affect the goal; backend-only or mechanical work does not need a design questionnaire.

- Identify the actor, situation, desired result and current friction from the user's brief and existing product evidence. Distinguish user research or observed behavior from assumptions. A use case proposed by the agent remains a proposal until accepted or supported by the request.
- Describe the primary journey and relevant alternate/error paths. Include discoverability, clear language and feedback, destructive-action recovery and loading/empty/error states when they change usability. Reuse established components and design conventions; do not redesign adjacent flows.
- Make accessibility acceptance concrete for affected interactions: keyboard operation and focus order/return, meaningful control names and error association, appropriate semantics, readable presentation and usable layout at relevant sizes or zoom. Derive any required standard/version from the project or user; do not claim compliance from source inspection alone.
- Separate functional success from a product hypothesis. Choose an observable success signal when outcome validation is requested, such as completion of a representative task; state the baseline and what evidence would change the decision. Do not invent user feedback, analytics or conversion improvements.
- Choose evidence proportional to the request: source/design inspection, a browser journey, assistive-technology checks or an authorized usability session. Identify unavailable devices/tools and simulated participants. A static mockup or automated accessibility check covers only its tested dimensions.

Return bounded acceptance, affected flows/states, verification method, evidence sources and assumptions. Material product choices need an answer; routine reversible implementation choices can follow project conventions. Do not schedule studies, contact users, add tracking or publish a prototype without matching authorization. Keep these requirements with the existing scope so implementation and review use the same agreement.
