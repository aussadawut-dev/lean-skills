# Lean Skills

[English](README.md) | **ภาษาไทย**

14 skills ที่ช่วยให้ coding agent วางแผน ลงมือทำ ทดสอบ และตรวจงานได้เป็นขั้นตอน
เลือกติดตั้งทั้งชุดหรือแค่ตัวเดียวก็ได้ **ไม่ต้องติดตั้ง Lean runtime หรือมีโฟลเดอร์ `.lean`**

ใช้กับ **Codex, Claude Code และ Antigravity** ผ่าน
[Skills CLI](https://github.com/vercel-labs/skills)

[คู่มือการใช้งานและ mapping flow](docs/guide.th.md)

## เริ่มต้นใช้งาน

เตรียม Node.js/npm เพื่อใช้คำสั่ง `npx` และติดตั้ง coding agent ที่ต้องการใช้งานก่อน
จากนั้นเลือกว่าจะติดตั้ง skills ไว้ที่ไหน:

| รูปแบบ | เหมาะกับ | ตัวเลือก |
| --- | --- | --- |
| Global | ต้องการใช้ skills ได้กับทุกโปรเจกต์ | ใส่ `-g` |
| เฉพาะโปรเจกต์ | ต้องการใช้ในโปรเจกต์ปัจจุบันเท่านั้น | ไม่ใส่ `-g` |

### ติดตั้งสำหรับทุกโปรเจกต์

```sh
npx skills add aussadawut-dev/lean-skills -g --skill '*' -a codex claude-code antigravity -y
```

### ติดตั้งเฉพาะโปรเจกต์

เปิด terminal ที่โฟลเดอร์หลักของโปรเจกต์ แล้วรัน:

```sh
npx skills add aussadawut-dev/lean-skills --skill '*' -a codex claude-code antigravity -y
```

### ติดตั้งแค่ skill เดียว

ตัวอย่าง: ติดตั้ง `lean-review` ให้ Codex เฉพาะโปรเจกต์ปัจจุบัน

```sh
npx skills add aussadawut-dev/lean-skills --skill lean-review -a codex -y
```

หากต้องการใช้ได้ทุกโปรเจกต์ ให้เพิ่ม `-g` ทุก skill ใช้แยกกันได้โดยไม่ต้องติดตั้งตัวอื่น

### ปรับคำสั่งให้ตรงกับการใช้งาน

- หลัง `-a` ใส่เฉพาะ agent ที่คุณใช้
- `--skill '*'` หมายถึงเลือกครบทั้ง 14 ตัว โดยต้องใส่เครื่องหมายคำพูดรอบ `'*'`
- `-y` คือข้ามคำถามยืนยัน หากต้องการเลือก agent ผ่านเมนู ให้ตัดทั้ง `-a` พร้อมรายชื่อ agent และ `-y` ออก
- หากต้องการดูรายการ skills โดยยังไม่ติดตั้ง ใช้คำสั่ง:

```sh
npx skills add aussadawut-dev/lean-skills --list
```

การติดตั้งแบบ global ไม่แก้ไฟล์ในโปรเจกต์ ส่วนการติดตั้งเฉพาะโปรเจกต์จะสร้างโฟลเดอร์
และลิงก์สำหรับให้ agent พบ skills เช่น `.agents/skills/` และ `.claude/skills/`
รวมถึงข้อมูลการติดตั้งตามที่ตัวติดตั้งใช้ โดยไม่เปลี่ยน global skills เดิม
ตรวจไฟล์ที่เพิ่มด้วย `git status` แล้วเลือก commit เพื่อใช้ร่วมกับทีม หรือเพิ่มใน ignore rules หากใช้ส่วนตัว

ถ้ามี skills ชื่อ `lean-*` อยู่แล้ว ให้เก็บสำเนาที่แก้เองก่อนติดตั้งทับ
skills ในโปรเจกต์อาจมีผลต่อการเลือกเวอร์ชันที่ agent เรียกใช้ด้วย
หากติดตั้งแล้วไม่พบ skills ให้โหลดใหม่หรือเริ่ม session ของ agent อีกครั้ง

## เรียกใช้ skill

บอกชื่อ skill ที่ต้องการ หรือใช้รูปแบบคำสั่งของ agent:

| Agent | ตัวอย่าง |
| --- | --- |
| Codex | `$lean-run เพิ่ม pagination และตรวจ flow การใช้งานจนจบ` |
| Claude Code | `/lean-run เพิ่ม pagination และตรวจ flow การใช้งานจนจบ` |
| Agent อื่นที่รองรับ | `ใช้ lean-run เพิ่ม pagination และตรวจ flow การใช้งานจนจบ` |

agent อาจเลือกใช้ skill จากคำอธิบายได้เองด้วย ไม่จำเป็นต้องเรียก `lean-init` ก่อน
และไม่ต้องติดตั้ง skill ตัวอื่นมาประกอบ

### คำสั่งเดียวตั้งแต่รับงานจนส่งมอบ

ใช้ `lean-run` เป็นทางเข้าหลักเมื่อต้องการให้ agent รับผิดชอบงานทั้งหมด:

```text
ใช้ lean-run แก้ checkout ที่ตัดเงินแล้วไม่สร้าง order
เคลียร์ requirement สำคัญก่อน ทำให้เห็นบั๊ก แก้ไข
และตรวจ flow จนสร้าง order สำเร็จ ส่งมอบเป็น PR
```

skill จะเคลียร์เรื่องสำคัญช่วงแรก แล้วทำงานที่ได้รับอนุญาตต่อจน implementation
ตรวจการเชื่อมต่อ ทบทวน และส่งมอบ โดยไม่ให้คุณเรียก skill ถัดไปเอง
หากพบข้อเท็จจริงใหม่ที่กระทบการตัดสินใจสำคัญ ยังอาจต้องถามเพิ่มเติม
หากไม่ระบุจุดส่งมอบ จะหมายถึงการเปลี่ยนแปลงที่ตรวจแล้วใน workspace ปัจจุบัน
การเปิด PR หรือ deploy ต้องมีคำสั่งอนุญาตและเครื่องมือที่เข้าถึงได้

`lean-run` เลือกใช้ skills ที่ติดตั้งไว้เท่าที่จำเป็น และทำขั้นตอนหลักเองได้เมื่อติดตั้งเดี่ยว
ส่วน `lean-task` ยังเป็นขั้นตอน implementation ที่ใช้เดี่ยวได้ เลือกเมื่ออยากใช้ขั้นตอนนั้นโดยตรง
ทั้งคู่ไม่ต้องติดตั้ง runtime ตัวควบคุมเก็บการตัดสินใจและจำนวนรอบแก้ไขข้ามขั้นตอน
ไม่ค้นโปรเจกต์ซ้ำโดยไม่มีเหตุ และหยุดการลองซ้ำที่ไม่เกิดความคืบหน้า
ไม่ได้รับประกันว่าทุกงานจะสำเร็จ: DONE ต้องมีหลักฐานครบตามเงื่อนไขบังคับ
BLOCKED หมายถึงขาดสิ่งจำเป็น และ FAILED หมายถึงยังมีความล้มเหลวที่ยืนยันแล้ว
ต้องเปิดเผยส่วนที่จำลองระบบภายนอกและขอบเขตที่ยังไม่ได้ทดสอบ

### เลือกโมเดลให้เหมาะกับงานที่แบ่ง

เมื่อได้รับอนุญาตและการแบ่งงานช่วยให้งานเสร็จ ตัวควบคุมจะเลือก model และ reasoning effort
ให้แต่ละงานจากความสามารถที่ provider ปัจจุบันเปิดให้ใช้จริง โดยใช้ตัวเลือกที่ผู้ใช้ระบุ
หรือ mapping ของโปรเจกต์ก่อน งานแก้เล็ก งาน implementation และงาน review ซับซ้อน
อาจใช้ความสามารถต่างกัน ไม่บังคับใช้สเกลขนาดเดียวกันข้าม provider
งานเล็กทำใน agent หลักได้ และโดยปริยายใช้ worker พร้อมกันไม่เกินหนึ่งตัว
เว้นแต่ขอทำงานขนาน ความละเอียดของขั้นตอนยังแยกจาก reasoning effort ของโมเดล

ชื่อที่แสดงใช้ `<taskname> - <model name>|<effort>` เช่น
`api_builder - gpt-6.1-sol|medium` หาก host จำกัดรูปแบบ ID ภายใน
จะแสดงชื่อเต็มในข้อความมอบหมายงานและรายงาน พร้อมเก็บ ID สำหรับติดต่อ agent
ไม่ได้หมายถึงการเปลี่ยนชื่อใน UI ของ host ที่ไม่มีช่องตั้งชื่อแสดงผล
Claude Code ใช้คำอธิบายงานของ Agent หรือ `--name` สำหรับ session ที่เปิดแยก
ส่วน Antigravity ใช้ Role โดยแยกจากชนิด agent และ ID ที่เครื่องมือส่งกลับ
ส่งชื่อเป็นข้อความ literal เสมอ เพื่อไม่ให้ `|` กลายเป็น shell pipeline

หากเครื่องมือรองรับ จะส่งค่า model/effort ชัดเจนตอน spawn และแยกค่าที่ขอออกจาก
ค่าที่ runtime ยืนยันจริง หากไม่มีตัวควบคุมหรือ metadata ต้องบอกตามจริง
ไม่เปลี่ยน provider ใช้ paid API สำรอง หรืออัปเดต configuration ของโมเดลเอง

## สิ่งที่ควรรู้

skills เป็นคำแนะนำให้ agent ทำงาน ไม่ได้ติดตั้งบริการเบื้องหลัง hooks อัตโนมัติ
ระบบควบคุมสิทธิ์ หรือหลักฐาน review ที่มีลายเซ็นรับรอง การตรวจงานและทดสอบจะทำผ่าน agent
โดยใช้เครื่องมือและกติกาของโปรเจกต์คุณ

ค่าความละเอียดและ repository ที่เลือกจะอยู่ในบทสนทนา เว้นแต่คุณขอให้บันทึกไว้
การแบ่งงานต้องมีเครื่องมือเรียก agent ส่วนการประเมินโมเดลต้องมีโจทย์ เครื่องมือ และสิทธิ์ที่เหมาะสม
ชุดนี้ไม่ได้รวมทะเบียนโมเดล ชุด benchmark หรือระบบคิวงาน
หากเครื่องมือไม่พร้อม agent ควรรายงานข้อจำกัดตามจริง

การติดตั้ง skill ไม่ได้ให้สิทธิ์ commit, push, deploy, ใช้ API ที่เสียเงิน
หรือเปลี่ยนสิทธิ์ของผู้ให้บริการโดยอัตโนมัติ ยังคงใช้คำสั่งของคุณและกติกาของโปรเจกต์เป็นหลัก

ดูหลักฐานใน [รายงานประเมินวันที่ 2026-11-01](tests/results/2026-11-01/README.md):
ทดลองกับ Codex ครบ 10 กรณีหลัก และทดลองส่วนเลือกโมเดลกับเงื่อนไขสำคัญของเวอร์ชันล่าสุดเพิ่ม
ส่วน Claude Code และ Antigravity ตรวจการติดตั้งและ
[ทดลองชื่อ subagent จริง](tests/results/2026-11-01-naming/README.md) รวมช่องว่าง `-` และ `|` แล้ว
แต่ยังไม่ได้ทดลองชุด workflow e2e เต็มบนสองเจ้านี้
รายงานแยกค่าของโมเดลที่ร้องขอออกจากข้อมูล backend ที่ runtime เปิดเผยจริง

## สำหรับผู้ร่วมพัฒนา

clone repository นี้ แล้วรันจากโฟลเดอร์หลักเพื่อลอง skills ที่แก้ในเครื่อง:

```sh
npx skills add ./ --skill '*' -a codex claude-code antigravity -y
```

ตรวจงานด้วย Python และ Node.js/npm:

```sh
python3 -m unittest discover -s tests -v
python3 tests/install_smoke.py
```

คำสั่งแรกใช้ standard library ของ Python ส่วน smoke test ใช้ `skills@1.7.4` ผ่าน `npx`
จึงต้องเข้าถึง registry ได้หรือมีแพ็กเกจใน cache การทดสอบครอบคลุมติดตั้งครบชุดและติดตั้งเดี่ยวทั้ง 14 ตัว
ทั้งแบบ global และเฉพาะโปรเจกต์ รวม **28 กรณี** ในโฟลเดอร์ผู้ใช้และโปรเจกต์จำลอง
ตรวจทั้งเนื้อหาและการแยกขอบเขตการติดตั้ง โดยไม่แก้ global skills จริงและไม่เรียก LLM
CI รันการตรวจทั้งสองคำสั่งนี้

การทดสอบนี้ยืนยันโครงสร้างแพ็กเกจและการติดตั้ง ไม่ได้ยืนยันพฤติกรรมของ agent
ใช้ [กรณีประเมินพฤติกรรม](tests/behavioral.md) ทดลองกับ agent ในพื้นที่แยก
และบันทึก host/model ผลงาน และผลตรวจที่เกิดขึ้นจริง การไล่อ่านสถานการณ์กับคำแนะนำ
ไม่เท่ากับการทดลอง agent จริงหรือหลักฐานว่าใช้งานได้เท่ากันทุก agent
เมื่อแก้คู่มือ ให้ปรับภาษาอังกฤษและภาษาไทยให้ตรงกัน โดยไฟล์ skill ยังคงเป็นภาษาอังกฤษ
